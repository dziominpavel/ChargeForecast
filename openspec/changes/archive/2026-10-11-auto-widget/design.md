## Context

См. proposal.md — Why. Технический контекст текущего состояния:

- `ChargeForecastApplication.onCreate()` создаёт `BatteryMonitor` и `ChargeSessionMonitor` и запускает монитор; `Application.onCreate()` выполняется при старте **любой** компоненты, включая сервис. Владельцем остаётся Application — перестраивать DI не нужно.
- `SessionViewModel` берёт `app.sessionMonitor()` — единственный экземпляр на процесс. Второго движка не появляется ни в одном из новых компонентов.
- `ForecastText.formatRemaining(context, remainingSec)` — чистая функция от `Context`, не зависит от Compose: форматирование времени переиспользуется вне экрана.
- `BatterySnapshot.currentMa` **сознательно отсекает** разряд: `takeIf { it > 0 && (charging || full) }`. Датчик отдаёт отрицательный ток, снапшот его выбрасывает.
- `SessionCache` — SharedPreferences без зависимостей, уже держит ёмкость, сводку, кривую по `chargeType` и буфер истории последних 5 сессий (после `history-prior-blend`).
- Платформенные стены, из-за которых архитектура именно такая: `ACTION_POWER_CONNECTED` не в списке исключения неявных broadcast (API 26+) — manifest-receiver его не получит; `startForegroundService()` из фона на API 31+ бросает `ForegroundServiceStartNotAllowedException`. Следствие: поймать кабель может только живой процесс.
- `targetSdk = 36`, `minSdk = 29`: требования foreground service type (API 34+) и `POST_NOTIFICATIONS` (API 33+) обязательны.
- Требования поведения — в спеках `background-tracking`, `battery-widget`, `discharge-estimate` (новые) и дельте `charge-forecast`.

## Goals / Non-Goals

**Goals:**
- Вставку кабеля замечает система, а не пользователь: отсчёт до 100% появляется без открытия приложения.
- Одно состояние на процесс: экран и виджет читают один и тот же `SessionState`.
- Постоянный мониторинг не оплачивается постоянными пробуждениями: в простое опрос остановлен.
- Оценка оставшегося работы — из накопленного расхода, с честным состоянием сбора данных до набора опоры.
- Ни одной новой зависимости.

**Non-Goals:**
- Точность разрядной оценки: она приблизительная по природе (расход зависит от будущего использования). Точность — отдельная задача, за пределами этого change.
- Точная модель расхода по категориям приложений/экрану: среднее по всему недавнему периоду, без сегментации.
- Профили «зарядка + кабель» (п.6 дорожной карты), история сессий в UI, настройки — остаются на будущее.
- Полноценная поверхность прогноза в уведомлении: уведомление сервиса служебное.
- Автозапуск Activity, full-screen intent, подсветка экрана при подключении.

## Decisions

### D1. Постоянный foreground service, не manifest-receiver и не WorkManager
`ACTION_POWER_CONNECTED` manifest-receiver'у не доставляется (нет в исключениях неявных broadcast, API 26+), а API 31+ запрещает поднимать foreground service из фона. Значит единственный путь — процесс, живущий **до** подключения, с receiver'ом, зарегистрированным в рантайме (`Context.registerReceiver` работает для любых broadcast, включая неявные).

Альтернативы отвергнуты: manifest-receiver + `startForegroundService()` — не сработает по обеим стенам; WorkManager периодической задачей — минимальный интервал 15 минут, отсчёт «до 100%» за это время устаревает многократно; `JobScheduler` с `setTriggerContentUpdateDelay` — привязан к content observer, у батареи его нет.

### D2. Время жизни сервиса: старт при открытии приложения + рестарт по `BOOT_COMPLETED`
Сервис обязан жить всё время, пока автодетект нужен: после его остановки процесс умирает и следующая вставка кабеля проходит незамеченной. Старт вызывается из `Activity.onCreate()` (единственное место, где платформа гарантированно разрешает запуск foreground service). После перезагрузки сервис поднимает manifest-receiver на `RECEIVE_BOOT_COMPLETED`.

Альтернатива «стартовать только на время зарядки» отвергнута: чтобы поймать **начало** зарядки, сервис должен быть жив до неё — циклическая зависимость. Единственный выход — постоянный сервис.

### D3. Уведомление сервиса — канал низкой важности, служебное
Канал `IMPORTANCE_MIN`: без звука, без всплешки, недоступен для смахивания (требование foreground service). Содержимое — подтверждение работы фонового слежения, **не** прогноз: поверхность прогноза — виджет и экран. Это сознательное решение, а не компромисс: уведомление придётся терпеть всегда, поэтому оно не должно конкурировать с продуктом.

Альтернатива «спрятать уведомление, отклонив `POST_NOTIFICATIONS`» отвергнута как основной путь: это обход системного ограничения, а не поведение; отказ в разрешении остаётся сценарием деградации (сервис продолжает работать), а не способом его спрятать.

### D4. Виджет на `RemoteViews`/`AppWidgetProvider`, без Glance
Виджет — два текстовых поля и уровень; Glance добавил бы зависимость и свои особенности обновления ради того, что `RemoteViews` делает нативно. Проект принципиально без сторонних зависимостей — сохраняем. Форматирование времени переиспользуется из `ForecastText`.

### D5. Обновление виджета — push от состояния, а не `updatePeriodMillis`
Минимальный системный интервал обновления виджета — 30 минут; для отсчёта «до 100%» это неприемлимо. Виджет обновляется из того же `collect(sessionMonitor.state)`, что и уведомление сервиса: на каждом изменении отрендеренной строки, с троттлингом (минимальный интервал ~15 с во время зарядки). Переходы (подключение, отключение, полный заряд) обходят троттлинг — реагирование в секунды.

### D6. Application владеет монитором и оценщиком; компоненты только читают
`DischargeEstimator` создаётся в `ChargeForecastApplication` рядом с `SessionCache` и передаётся в сервис. Ни сервис, ни виджет не создают собственных экземпляров монитора — иначе экран и виджет разошлись бы.

### D7. Ошибки — во flow, не в StateFlow
`SessionViewModel.dismissError()` сейчас делает `reportError(null)`, то есть пишет в `MutableStateFlow`. При нескольких подписчиках (экран, сервис, виджет) сброс одной подпиской очистит ошибку у остальных, а повторное подписывание переиграет устаревшую ошибку. Ошибки переводятся в `MutableSharedFlow` (replay 0) с колбэком `dismiss` — каждый подписчик получает событие один раз.

### D8. Ток разряда — отдельное поле снапшота, не переписывание `currentMa`
`currentMa` сегодня — строго положительный ток зарядки, и от него зависят расчёт скорости, пик тока, `sameReading` и строка электрики на экране. Менять знаковую семантику поля — всплеск риска по всему конвейеру. Вместо этого в `BatteryExtras`/`BatterySnapshot` добавляется отдельное поле тока разряда, заполняемое когда `!charging`: нулевой риск регрессии, оценщик получает свои данные.

### D9. `DischargeEstimator` — чистый модуль, накопитель в `SessionCache`
Как `SpeedFusion`/`HistoryBlender`: расчёт без Android-зависимостей, тестируем на JVM. Накопление — только на интервалах `!isPlugged`; переходы зарядка↔разряд в накопитель не попадают. Состояние (накопленные мкА·ч, метка последнего замера, сглаженный ток) персистится в `SessionCache` плоскими ключами в стиле существующих: переживает убийство процесса OEM-оболочкой и перезагрузку. Промежуток между последним замером и загрузкой **исключается** из накопления — иначе ночь сном записалась бы как расход.

Полуокно усреднения (EWMA, порядка суток) — константа: бурный вечер сдвигает оценку заметно, неделя тишины — постепенно. Это единственный управляющий параметр, его калибровка — на устройстве автора.

### D10. Опрос в простое останавливается, пробуждение — по broadcast
После появления сервиса и его runtime-receiver'а циклы `BatteryMonitor` (10 с) и `ChargeSessionMonitor` (30 с) в простое останавливаются, пробуждение — по `ACTION_POWER_CONNECTED`. Круглосуточный опрос был бы оправдан только на экране; на живом 24/7 процессе это постоянные пробуждения.

**Порядок обязателен:** приостанавливать опрос раньше, чем сервис и receiver готовы, — значит получить приложение, которое не замечает кабель вообще.

## Risks / Trade-offs

- [OEM-оболочка (Huawei/EMUI, Xiaomi) убивает foreground service] → проверка на устройстве автора обязательна до релиза: зарядить телефон, залочить, подождать 10 минут, убедиться, что виджет обновляется. Митигация — ручная настройка «защищённых приложений» на устройстве; кодом лечится лишь обнаружением остановки (виджет показывает состояние «слежение остановлено», а не замороженное число).
- [Отказ в `POST_NOTIFICATIONS`] → сервис продолжает работать, уведомление не показывается; Android показывает строку о работающем приложении в настройках. Экран приложения объясняет состояние.
- [Заморозка виджета при убитом процессе] → виджет обязан отличать «нет данных» от «данные устарели»: при остановленном слежении — состояние остановки, а не последнее число. Риск честного вида, а не точности.
- [Оценка разряда врёт при смене режима] → принимается осознанно (решение автора): среднее смещается с задержкой, равной окну усреднения. Спека требует приблизительности, а не точности.
- [1 Гц-обновление уведомления и виджета во время зарядки] → троттлинг виджета до ~15 с (D5); уведомление сервиса обновляется по той же логике. Количество binder-вызовов ограничено, экран остаётся 1 Гц.
- [Регрессия конвейера при добавлении поля в снапшот] → поле отдельное (D8), `sameReading`, расчёт скорости и строка электрики не затронуты; `BatterySnapshotTest` закрывает маппинг разрядного тока.
- [Первое открытие после установки — накопителя расхода нет] → виджет показывает состояние сбора данных; после набора опоры цифра появляется. Это ожидаемое поведение, а не дефект.
- [Зависимость от `history-prior-blend`] → снята: change реализован в рабочем дереве (132 теста), «число с первой секунды» для отсчёта уже есть.

## Migration Plan

Пофазно, каждая фаза независимо тестируется и откатывается revert'ом:

1. **Данные разряда** — поле тока разряда в снапшоте + `DischargeEstimator` + ключи `SessionCache` + JVM-тесты. Ничто это не читает — нулевой риск для конвейера.
2. **Сервис** — `ChargeForecastService`, `BootCompletedReceiver`, разрешения и foreground service type в манифесте, минимальное уведомление. Экран не меняется.
3. **Пробуждение вместо опроса** (дельта `charge-forecast`) — только после фазы 2: иначе приложение перестаёт замечать кабель.
4. **Виджет** — provider, layout, info-xml, пайплайн обновления от состояния.
5. **Сверка** — `.\gradlew.bat test`, `python scripts/check-version.py`, проверка на устройстве автора (EMUI, перезагрузка, полный цикл зарядки), запись пользовательского блока changelog в `## [Unreleased]` (поведение видимое — пункт пишется в момент работы).

Фаза 3 без фазы 2 запрещена; фазы 1, 2 и 4 независимы.

## Open Questions

- Полуокно усреднения расхода и минимальное число замеров до показа цифры — калибровать на реальном устройстве; значения не меняют спеку, только константы.
- Стоит ли добавить переключатель «фоновое слежение включено» в настройках: даёт пользователю выход из постоянного сервиса ценой автодетекта. Меняет набор поведения виджета — отложить до реальной надобности.
- Размер и компоновка виджета (1×1 / 2×1) — уточнить визуально на устройстве; не влияет на требования.
