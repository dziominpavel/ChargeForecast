## Context

> **Решение автора (05.09.2026):** функционал шторки (уведомление + ForegroundService) удалён из продукта целиком — этот design описывает историческое состояние change'а. Актуален только экранный конвейер «батарея → скорость → прогноз → экран».

См. `proposal.md` — Why. Текущее состояние: `MainActivity` + `ChargeForecastApp()` — заглушка без ViewModel, чтения батареи нет, `AndroidManifest.xml` без разрешений, `openspec/specs/` пуст. Ограничения: minSdk 29 / target 36, один модуль `:app`, тема Volt через токены, PowerShell/UTF-8, тексты на русском.

## Goals / Non-Goals

**Goals:**
- Live-конвейер «батарея → скорость → прогноз → экран» с обновлением каждую секунду на зарядке.
- Максимальная точность из доступных сигналов с честной вилкой `±`.
- Не падать и видимо сообщать об ошибках, когда датчики недоступны.

**Non-Goals:**
- История сессий, профили «блок + кабель», сравнение и рейтинг — исключены по решению из explore. Зависимость `datastore-preferences` удаляется из каталога версий и `app/build.gradle.kts` (неиспользуемый груз).
- Виджет, автозапуск экрана при втыкании, звуки/анимации уведомления.
- Новые библиотеки сверх уже подключённых (`lifecycle-service`, `viewmodel-compose`, `core-ktx`).

## Decisions

- **Источник данных — `ACTION_BATTERY_CHANGED` (sticky) + `BatteryManager`, без опроса в цикле.** Почему: система сама шлёт intent при изменении батареи, это дешевле и точнее таймера; альтернатива (периодический `getProperty`) жрёт батарею и пропускает события. Репозиторий подписывается на sticky-intent в корутине и отдаёт `StateFlow<BatterySnapshot>` (level, status, plugged, temp, currentNow, voltage — nullable). Плюс лёгкий тик опроса sticky-состояния раз в 10 сек: broadcast приходит только при изменениях, а ток/температура плывут непрерывно; чаще (раз в секунду) смысла нет — уровень идёт шагом 1%.
- **Скорость — три сигнала по лестнице зрелости: ток → дельта счётчика → дельта уровня.** Почему: уровень идёт шагом 1% и молчит минуты; ток (`CURRENT_NOW`) с ёмкостью даёт цифры с секунд, но плавает; дельта счётчика (мкА·ч) — тот же замер, что по уровню, но видна за 30–60 сек. Берём пик тока сессии (рампа блока + расход экрана занижают текущий), ёмкость — живой трекер `Δсчётчик/Δуровень`, иначе sysfs `charge_full_design` (best-effort), иначе кэш. Все гейты — физический минимум: любому спидометру нужны две точки, интервал — тик опроса 10 сек, меньше некуда; шум ранних цифр гасится весом по возрасту и статусом «примерно». Формула: instant = ток_max/ёмкость·100/60; measured = уровень-дельта ?: счётчик-дельта; итог = instant·(1−w) + measured·w, w = возраст/10 мин. «Точно» раньше 10 мин, если оценки сошлись в ±20% при возрасте от 3 мин. Нет живых датчиков или их показания в мусорной рампе — опорой становится скорость прошлой сессии из кэша (на разгоне — максимум из живой и кэша: рампа занижает, кэш ближе к правде). Порог доверия 0.05 %/мин ниже 80%: медленнее — мусор рампы, показываем «собираю данные», а не «1000 часов»; доводка исключена. Без тока/счётчика/sysfs/кэша — только дельта уровня с fallback.
- **Прогноз — кусочная экстраполяция: линейная до 80%, замедленная после.** `(100 − level)/speed`, при level ≥ 80 применяется коэффициент доводки ~0.5 (уточняется spike-замером на реальном устройстве). Готовность — по данным, а не по wall-времени: нет ни мгновенной, ни измеренной скорости — «собираю данные», есть оценка и возраст <10 мин — «примерно», измеренная 10+ — «точно». Процентная «точность» и числовая вилка «±N» отвергнуты как показ: подразумевают модель, которой нет, — стадии словами проверяются поведением. Альтернатива «одна формула на всё» врёт на хвосте на 20–40 мин; альтернатива «жёсткие 3 минуты молчания» прятала цифры при уже набранных процентах.
- **Показ — один `ForegroundService` (тип `specialUse`/`connectedDevice` по target 36) + один канал `NotificationManager`, экран читает тот же `StateFlow` через `ViewModel`.** Почему: single source of truth — экран и шторка не расходятся; сервис обязателен для ongoing-уведомления. Тап по уведомлению открывает `MainActivity`. Обновление уведомления не чаще 30 сек (не душить систему), не реже 60 сек. Сервис пишет пульс (метку времени) в кэш при каждом обновлении; экран по пульсу старше 90 сек показывает «Шторка не обновляется…» — видимая диагностика вместо тишины.
- **Старт/стоп — `BroadcastReceiver` на `POWER_CONNECTED/DISCONNECTED` + проверка `isCharging` при старте приложения.** Почему: покрывает кейс «приложение убито, воткнули кабель» и «воткнули до установки». Fallback: если broadcast пропущен, экран сам поднимает сервис при виде charging-статуса. Важно: на Android 12+ старт FGS из фона запрещён без exemption — receiver ловит `SecurityException` и вместо сервиса показывает обычное уведомление «откройте приложение для прогноза»; открытие приложения (foreground) стартует FGS штатно.
- **Ошибки — видимые, не silent.** `POST_NOTIFICATIONS` (33+) запрашивается автоматически при первом запуске (без него нет ни шторки, ни fallback) и повторно по кнопке; при выдаче позже сервис доподнимается без перезапуска. Отказ → данные только на экране + кнопка повтора. Исключения сервиса/репозитория → Snackbar/текст, по AGENTS.md.

## Risks / Trade-offs

- [Risk] Уровень с шагом 1% шумит первые минуты → прогноз прыгает → Митигация: статус «собираю данные», сглаживание, не показывать цифры до 2 точек изменения.
- [Risk] Хвост 80→100% сильно нелинеен и зависит от температуры/производителя → Митигация: коэффициент доводки + вилка `±`, калибровка на реальном устройстве автора.
- [Risk] Производители режут `CURRENT_NOW` (0 или Long.MIN) → Митигация: nullable-модель, fallback только на дельту, unit-тесты на оба пути.
- [Risk] Система убивает/душит сервис (Doze, FGS-ограничения 12+) → Митигация: корректный тип FGS, `START_STICKY`, видимая ошибка при отказе старта.
- [Risk] `BUILD_DATE` в `build.gradle.kts` инвалидирует кэш каждую сборку → Митигация: не трогать в этом change, вынести в отдельный техдолг.
- [Trade-off] Без истории точность на хвосте на ~10% ниже, чем могла бы → принято ради простоты и отсутствия ручного тегирования.

## Migration Plan

- Чисто аддитивный change: новый battery-слой, сервис, receiver, ViewModel; существующая заглушка заменяется экраном сессии. Откат — удалить сервис/receiver из манифеста и вернуть заглушку. Данных/миграций нет.

## Open Questions

- Точный коэффициент доводки после 80% и оптимальное окно (10 vs 15 мин) — калибруется spike-замером на реальном устройстве автора, на спеки и разбивку задач не влияет.
- Точный тип FGS под target 36 (`specialUse` с property vs `connectedDevice`) — решается при реализации по lint/политике Play, поведение спеки не меняет.
