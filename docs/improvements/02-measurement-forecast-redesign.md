# Проблема 2: логика измерений и прогноза — разбор и перепроектирование

Симптомы от автора (живая сессия):
1. «Почему меняется информация по прошлой зарядке? Она всегда равна текущей?»
2. «Было написано "осталось 25 мин", потом резко стало 1 ч 25 мин».
3. «Измерения должны идти раз в секунду с нулевой секунды и быть живыми».

Все три симптома воспроизводятся чтением кода — ниже каждый привязан
к конкретным строкам. Ревизия анализа: `1ddbdb9`.

---

## 1. Найденные дефекты

### Д1. «Прошлая зарядка» перезаписывается текущей сессией

`ChargeSessionMonitor.kt:91`:
```kotlin
private fun lastSpeed(): Float? = lastMeasuredSpeed ?: cache?.loadLastSpeed()
```
`lastMeasuredSpeed` обновляется **каждый тик текущей сессии**
(ChargeSessionMonitor.kt:131-136: вычислили measured → сразу `saveLastSpeed`).
Через 10–20 секунд после втыкания `lastMeasuredSpeed != null`, и строка
«прошлая зарядка» (SessionScreen.kt:194-208) начинает показывать **текущую
живую скорость** — отсюда «всегда равна текущей».

Побочный эффект хуже: приор для следующей сессии портится. `saveLastSpeed()`
пишется непрерывно, поэтому в кэш уходит значение **на момент вытыкания
кабеля**. Выткнул на 85% в фазе доводки (CV) → в кэше заниженная вдвое
скорость → следующая сессия стартует с пессимистичного приора.

### Д2. Прыжок «25 мин → 1 ч 25 мин» — три усилителя скачка

```
остаток
  ^
  |                                   ступенька x2 на границе 79%->80%
  |                                   ChargeForecaster.kt:86-89
1ч25|...................................____
    |                          ______--/
    |                    _____--
    |              _____-    <- бленд 10 мин: вес ползёт от
    |         ____-            ОПТИМИСТИЧНОГО instant к честному
    |     ___-                 measured -> остаток растёт непрерывно
    |  __-                     ChargeForecaster.kt:49-57
 25 |--
    +--------------------------------------> возраст сессии
   0                                          10 мин
```

a) **Старт заведомо занижен**: instant-оценка = `max(пик_тока_сессии, приор)`
   (InstantSpeedEstimator.kt:27-31 — берётся МАКСИМУМ тока; :39-46 —
   максимум из опор). Пик тока систематически выше среднего → «25 мин».
b) **Бленд по возрасту**: 10 минут вес ползёт от оптимистичного instant
   к честному measured → показанный остаток непрерывно растёт.
c) **Ступенька доводки**: на границе 79%→80% остаток мгновенно
   **удваивается** (`base /= TAPER_FACTOR`, ChargeForecaster.kt:87-89).

Все три эффекта складываются в один скачок в 3+ раза.

### Д3. Квантование уровня 1% ломает ранний замер

Уровень заряда идёт шагом 1%. `ChargeSpeedCalculator` работает по уровню:
ранний сэмпл «1% за 12 сек» даёт мусорные 5 %/мин; фильтр выбросов
(ChargeSpeedCalculator.kt:51-57) при 1–2 сэмплах не работает — медиана
из одного элемента, отбрасывать нечего. Реальное разрешение есть у
счётчика `CHARGE_COUNTER` (мкА·ч, обновляется ~1 Гц), но он задействован
только как fallback (ChargeSessionMonitor.kt:131-132).

### Д4. Измерения не «живые»

| Где | Сейчас | Последствие |
|---|---|---|
| Опрос батареи | 10 сек (BatteryMonitor.kt:133) | ток/счётчик приходят рывками |
| Тикер состояния | 30 сек (ChargeSessionMonitor.kt:170) | возраст сессии/точность обновляются редко |
| Шторка | троттлинг 30 сек (NotificationHelper.kt:27) | пользователь видит редкие скачки |

Комментарий в BatteryMonitor.kt:54-57 («раз в секунду смысла нет») верен
только для уровня (шаг 1%) и **неверен** для тока и счётчика: они
обновляются ~1 Гц, и на зарядке экономить батарею бессмысленно — телефон
у розетки. Требование автора «раз в секунду с нулевой секунды» выполнимо
и правильно.

### Д5. Нулевая секунда размыта

Сессия стартует не от втыкания кабеля, а от первого снимка с
`isCharging || isFull` (ChargeSessionMonitor.kt:95, 109-115). Во время
рампы зарядника (0.1 → 1.5 А за первые десятки секунд) статус CHARGING
запаздывает → «секунда ноль» уезжает, возраст сессии врёт.

### Д6. Дополнительно (robustness)

- Время везде `System.currentTimeMillis` — при подстройке часов сетью
  скорости/возраст скачут. Для расчётов нужен `SystemClock.elapsedRealtime`.
- Оценка ёмкости `estimateCapacityUah` (InstantSpeedEstimator.kt:11-15)
  делит счётчик на уровень — при level=1% ошибка ×2. Sanity-границы
  есть только в CapacityTracker, стартовая оценка может быть дикой.
- `SharingStarted.Eagerly` + монитор на уровне Application — ок, не трогаем.

## 2. Целевой конвейер измерений

```
ПОКА КАБЕЛЬ ВОТКНУТ (на зарядке экономить батарею не нужно):

КАЖДУЮ СЕКУНДУ (SystemClock.elapsedRealtime):
  readSnapshot: CURRENT_NOW, CHARGE_COUNTER, level, status
       |
       v
  +-------------------- ТРИ НЕЗАВИСИМЫХ СПИДОМЕТРА --------------------+
  | S1. counterRate:  дельта CHARGE_COUNTER (мкА*ч/мин)               |
  |     окно 30 сек (отклик) + 2 мин (стабильность), МНК по окну      |
  |     (least squares вместо двух концевых точек -> шум /5)          |
  | S2. currentRate:  EMA тока (tau ~15 сек) / ёмкость -> %/мин       |
  |     НЕ пик! EMA гасит рампу и выбросы драйвера                    |
  | S3. levelRate:    дельта уровня (как сейчас) - только fallback    |
  +--------------------------------------------------------------------+
       |
       v
  FUSION: 0-20 сек   -> S2 (единственный доступный) + метка "измеряю"
          20-90 сек  -> S1(30с) с доминантным весом, S2 кросс-чек
          >90 сек    -> S1(2м) доминирует, S3 кросс-чек
          расхождение S1/S2 > 40% -> "уточняю", вес у более
          консервативной (меньшей) скорости
       |
       v
  ОСТАТОК В мкА*ч (обход квантования 1%):
    remainingUah = capacityUah - chargeCounterUah
    remainingMin = remainingUah / rateUahPerMin
    level >= 80 (или CV по падению тока): интеграл по 5%-корзинам
    с кривой rate(level) (см. раздел 3)
       |
       v
  +---------------- ФИЛЬТР ПОКАЗА (анти-скачок) ----------------------+
  | 1) EMA сырой оценки, tau=45 сек                                   |
  | 2) квантование по ярусу точности (см. 2.1)                        |
  | 3) храповик: вверх ТОЛЬКО при устойчивом пересмотре модели,      |
  |    вниз - свободно => показанный остаток почти монотонно убывает  |
  +--------------------------------------------------------------------+
       |
       +--> экран: тик 1 сек (StateFlow уже есть, просто чаще)
       +--> шторка: 5-15 сек адаптивно (или при видимом изменении текста)
```

### 2.1 Ярусы точности и округление (ключ к «не скачет»)

| Возраст сессии | Источник | Метка | Округление остатка |
|---|---|---|---|
| 0–20 сек | S2 (ток) + приор прошлой сессии | «Измеряю… N с» | не показывать остаток, только ток/ватты/уровень |
| 20–90 сек | S1(30с) | «Примерно» | 10 мин, с «~» |
| 90 сек–10 мин | S1(2м)+S2 | «Примерно» | 5 мин |
| >10 мин и S1≈S2 (±20%) | S1(2м) | «Точно» | 1 мин |

Грубое округление ранних цифр — это честность: «~50 мин» не должно
превращаться в «1 ч 25 мин», потому что обе цифры из одного яруса.

### 2.2 Храповик показа (формально)

```
displayed(0) = первое квантованное значение
на каждом тике:
  candidate = quantize(ema(rawEstimate))
  если candidate < displayed - elapsedSinceLastTick:
      displayed = candidate            # снижаем свободно (время идёт)
  иначе если candidate > displayed И
          (candidate - displayed)/displayed > 25% И
          условие держится 3 тика подряд:
      displayed = candidate            # пересмотр модели, редко
  иначе: displayed убывает только на прошедшее время
```

Property-тест: при постоянной истинной скорости показанный остаток
не возрастает после 90-й секунды (кроме перехода на ярус точности).

### 2.3 Жизненный цикл сессии (честная секунда ноль)

```
POWER_CONNECTED / переход isPlugged=false->true
  -> plugDetectedAtMs = elapsedRealtime()      <- секунда ноль
  -> "Измеряю…" с живым счётчиком секунд (видно, что система жива)
первый снимок isCharging
  -> chargingConfirmedAtMs (диагностика рампы)
замеры копим с plugDetectedAtMs; рампу помечаем, но ток не выбрасываем
  (S2 на EMA сам её сгладит)
```

## 3. Доводка (CV-фаза) без ступеньки

Вместо бинарного «после 80% в два раза медленнее» (TAPER_FACTOR=0.5):

```
непрерывная кривая множителей скорости по 5%-корзинам уровня:

корзина:   80-85  85-90  90-95  95-100
множитель:  0.55   0.40   0.30   0.20    <- дефолт, КАЛИБРОВАТЬ (задача 2.3)

остаток = сумма по корзинам: energy(bin) / (baseRate * factor(bin))

кривая обучается: текущая сессия + прошлые сессии того же профиля
(тип подключения AC/USB/wireless); персистентно в SessionCache
```

Бонус: кривая по корзинам — это и есть будущий «профиль зарядки+кабель»
из дорожной карты AGENTS.md (п.6), закладываем модель сразу.

## 4. «Прошлая сессия» — замороженная сводка

Правило: текущая сессия НИКОГДА не пишет в поля прошлой. Запись — один
раз, в конце сессии (переход active→inactive, ChargeSessionMonitor.kt:96-107).

```kotlin
data class SessionSummary(
    val endedAtMs: Long,
    val durationMs: Long,
    val gainedPct: Int,
    val avgCcSpeedPctPerMin: Float,   // средняя CC-фазы: сэмплы ПОСЛЕ рампы
                                      // (+2 мин от старта) и ДО 80%/CV
    val peakCurrentMa: Float?,
    val chargeType: ChargeType
)
```

- `SessionCache`: новые ключи под сводку (SharedPreferences, как сейчас;
  JSON-строкой или плоскими ключами — без новых зависимостей).
- `saveLastSpeed` во время сессии — УДАЛИТЬ (ChargeSessionMonitor.kt:133-136);
  `lastSpeed()` — читать только кэш (ChargeSessionMonitor.kt:91).
- UI: отдельная карточка «Прошлая зарядка: 1.2 %/мин, 45 мин, +38%»,
  не смешивать с текущими цифрами.

## 6. План по фазам (каждая фаза самостоятельно поставляема)

### Фаза 0 — быстрые победы (~30–60 мин, без переписки конвейера)
1. Д1: `saveLastSpeed` только в конце сессии; `lastSpeed()` — только кэш;
   в SessionSummary — avgCcSpeed без рампы/доводки.
2. Д2a: `updateSessionMax` → EMA тока (tau=15 сек).
3. Д2c: ступенька → линейная интерполяция множителя 1.0→0.5 между 80% и 90%
   (временно, до фазы 2) — скачок ×2 исчезает уже здесь.
4. Тесты: SessionSummary-сохранение, EMA, интерполяция; регрессия
   «25→85 мин» на синтетике (постоянная скорость, рампа тока).

Результат: симптомы 1 и 2 почти ушли, конвейер прежний.

### Фаза 1 — секундный конвейер
1. `SystemClock.elapsedRealtime` для всех расчётов (clock уже инжектится
   в мониторы — поменять дефолт).
2. POLL_MS/TICKER 1 сек на зарядке; `sameReading` не мешает (ток плывёт).
3. S1: МНК (least squares) по окну счётчика 30 сек + 2 мин; S2: EMA;
   fusion по таблице 2.1; S3 — fallback.
4. Остаток в мкА·ч (где есть счётчик); ярусы точности + округление;
   храповик показа.
5. Жизненный цикл: plugDetectedAtMs от POWER_CONNECTED.
6. Тесты: property-тест монотонности показа; replay-сессии
   (ровная, рампа Huawei P60 Pro, шумный счётчик, без счётчика,
   без тока); обновить ChargeForecastTest/InstantSpeedTest/CounterSpeedTest
   под новые контракты; NotificationThrottleTest — адаптивный троттлинг.

Результат: симптом 3 закрыт, цифры живые с секунды 0.

### Фаза 2 — CV-кривая и профили

2. Интеграл остатка по корзинам вместо линейной экстраполяции.
3. Персист профилей по типу подключения (фундамент п.6 дорожной карты).

### Фаза 3 — юзабельность и калибровка

## 7. Критерии приёмки (финал, на устройстве автора)

1. Воткнул кабель: в первую секунду видны уровень, ток, ватты,
   «Измеряю…»; остаток — с ~20-й секунды, грубо округлённый.
2. «Прошлая зарядка» НЕ меняется во время текущей сессии (заморожена).
3. Запись экрана сессии: показанный остаток монотонно убывает
   (допустимы пересмотры ≤ 25%, ≤ 1 раза за сессию на ранней фазе).
4. Переход через 80%: остаток меняется плавно, без скачка ×2.
5. Прогноз «точно» (после 10 мин): ошибка финала ≤ ±10 мин на полной
   сессии устройства автора.
6. Разряд (кабель выткнут): опрос возвращается на 10 сек, шторка уходит.
7. `assembleDebug` + `test` зелёные; ни один unit-тест не удалён без
   замены эквивалентным под новый контракт.
