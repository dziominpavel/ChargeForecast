## Context

См. proposal.md — Why. Технический контекст текущего конвейера:

- `SpeedFusion.fuse()` принимает `priorPctPerMin` и использует его только в ярусе 0–20с через `max(credible, prior)` (`InstantSpeedEstimator.selectInstantSpeed`); на 20-й секунде приор исчезает скачком. Приор — одно `Float` из `KEY_LAST_SPEED` (сводка одной сессии).
- `SessionEngine` уже нормализует live-скорость в базовую опору линейной зоны (`baseRateEmaPctPerMin`, EMA α=0.05/тик) и передаёт её в `ChargeForecaster.forecast(baseRatePctPerMin=...)` — интеграл по корзинам доводки. Это готовая точка врезки смеси.
- `ChargeForecaster` гейтит выдачу цифр по `!isCharging` (строка 67), хотя сессия стартует от `isPlugged` — статус CHARGING может запаздывать.
- `DisplayFilter` принимает вверх только рывок +25% за 3 тика; ветка «кандидат выше показанного, но <25%» продолжает убывать показанное — источник «пилы» на любом плавном пересмотре модели вверх.
- Требования поведения — в спеке `charge-forecast` (дельта этого change). Тесты: `DisplayFilterTest` (property-тест «не возрастает при постоянной скорости», сид детерминирован), `SpeedFusionTest`, `SessionEngineTest`, `ChargeForecastTest`, `SessionCacheTest`.

## Goals / Non-Goals

**Goals:**
- Остаток с первой секунды при наличии истории; один непрерывный переход история → замеры (0–10с держим, 10–180с smoothstep, с 180с только живые данные).
- История — буфер последних 5 сессий на тип подключения, медиана, тот же гейт качества, что у сводки.
- Показанное значение идёт мелкими шагами вверх при плановых пересмотрах модели, не теряя защиты от мусорных всплесков и property-теста.
- Фаза 3-й минуты идентична текущему поведению (w=0) — ноль регрессий для существующих веток fusion/интеграла.

**Non-Goals:**
- Профили «зарядка + кабель», ручной выбор или авто-кластеризация зарядок (дорожная карта п.6) — ключ истории остаётся `chargeType`.
- Новая строка подписи точности «по истории»; отдельный UI истории сессий.
- Изменение яруса «Точно» (10 минут + согласие спидометров) и калибровка констант spike-замером (фаза 3 дорожной карты).

## Decisions

### D1. Смесь в пространстве базовой скорости, в точке `baseRatePctPerMin`
`base = w(t)·H + (1−w(t))·baseRateEma`, результат передаётся в `ChargeForecaster` как `baseRatePctPerMin`, показываемая скорость — `base · factor(level)`.

Альтернативы: смесь остатков в секундах (T = w·T_H + (1−w)·T_live) — отвергнута: остаток нелинейно зависит от скорости через интеграл корзин, смешивать надо причину (скорость), а не следствие; два слоя сглаживания (EMA + смесь) на «сырье» были бы труднокалибруемы. Смесь до fusion — отвергнута: fusion обязан оставаться чистым оценщиком живых спидометров, история — отдельный слой.

Живой вклад — уже сглаженная `baseRateEma` (существующая EMA), поэтому на выходе смеси один фильтр тренда, без удвоения.

### D2. Кривая веса: smoothstep с удержанием
```
w(t) = 1                             при t ≤ 10с         (t0)
u = (t − 10с) / 170с
w(t) = 1 − (3u² − 2u³)               при 10с < t < 180с  (T)
w(t) = 0                             при t ≥ 180с
```
Нулевая производная на обоих концах — без изломов на 10с и 180с. Линейная альтернатива (тот же диапазон) отвергнута: ступенька скорости изменения на границах даёт ускорение видимого дрейфа; экспонента отвергнута — не доходит до 0 (хвост не даёт «перехода завершён») и не даёт чистого 100%-удержания первые 10с.

Аппроксимация значений (для тестов-снапшотов): t=30с → w≈0.96, 60с → 0.79, 90с → 0.54, 120с → 0.28, 150с → 0.08.

`T = 180с` выбран не округленно: длинное окно S1(2м) заполняется к 2-й минуте, переход завершается ровно когда созревают сами замеры.

### D3. Апдейт-правила веса (поверх расписания)
```
w = schedule(t)
истории нет                 -> w = 0     (первая сессия: только живые данные)
live == null / < порога доверия -> w = 1  (рампа/нет датчиков: история несёт)
live «уточняю» (S1/S2 > 40%)   -> w = max(w, 0.5)
```
Отвергнут вариант «брать max(history, live)» в первом ярусе (текущий хак) — систематически завышает и не имеет непрерывного перехода.

### D4. Новый чистый модуль `HistoryBlender`
Объект/класс без Android-зависимостей в пакете `forecast`: `blend(historyBaseRate, liveBaseRate, refining, ageMs): Float?` и отдельно тестируемая `weightOf(ageMs): Float`. Все ветки D2/D3 покрываются JVM-тестами, как у `SpeedFusion`. `SpeedFusion` теряет параметр `priorPctPerMin` и ветку `selectInstantSpeed` — ярус 0 становится чистым S2 с обычным credible-фильтром.

### D5. История: кольцевой буфер на `chargeType` в `SessionCache`
Ключи плоские, в стиле существующих кривых: `hist_<TYPE>_<0..4>` + счётчик/флаг. Запись — в тот же момент, что и сводка (`buildSummary` вернул не-null → в буфер). Агрегат — медиана (устойчивость к одному выбросу; среднее отвергнуто: одна чудная сессия тянет оценку). Новые зависимости не вводятся (SharedPreferences, как и весь кэш).

Ленивая миграция: при первом чтении буфер пуст, а `loadSummary()` есть — засеять буфер её avgCcSpeed (та же добрая сессия, тот же гейт). Пользователь получает историю сразу после обновления, без периода «пусто».

### D6. Trend-gate в `DisplayFilter` — второй путь пересмотра вверх
Пути вверх:
1. **Рывок (существующий):** кандидат ≥ показано·1.25 и держится 3 тика.
2. **Тренд (новый):** медленная EMA сырого остатка (tau=60с) выросла относительно своего значения 60с назад больше чем на порог шума, условие держится K=3 тика подряд → принимаем кандидат (EMA tau=10с) каждый тик.

Почему долгое окно, а не «N тиков подряд вверх»: белый шум ±5% из property-теста даёт монотонные серии тиков регулярно — короткий триггер ломает тест. Разность медленной EMA через 60с окно шум гасит (ЭМА tau=60с дополнительно усредняет), а тренд смеси (сырой растёт ~2.7 сек/сек × 60с окно) проходит легко. Отвергнут вариант «разрешить ап-ревизии без порога» — открывает всплескам дорогу в показ; отвергнут «смягчить до +5% за 3 тика» — не отличает тренд от серии шумовых киков.

Константы: `TREND_WINDOW_MS = 60_000`, `TREND_TICKS = 3`, `TREND_NOISE_FLOOR_SEC` — калибруются парой тестов (property «не возрастает» на шуме + антипила «плавный пересмотр идёт шагами»), сиды детерминированы. Порог обязан удовлять обоим: для property-теста шумовой рост разности за 60с — единицы-десятки секунд, для смеси — сотни.

Контракт «вниз свободно» и property-тест «при постоянной истинной скорости не возрастает после 90с» сохраняются без изменений.

Уточнения по результатам реализации (фаза 3):
- **Ветка «кандидат выше показанного, но путь не открыт» держит показанное** (не убывает по времени): спека требует «без ложных падений» при росте модели — пауза в ожидании тренда лучше падения вслед за растущей моделью. Убывание по времени остаётся для ветки без данных (raw = null), property-тест держится (удержание не возрастает).
- **Крупное падение кандидата (`TREND_RESET_DROP_SEC = 60` сек) обнуляет окно тренда**: иначе разность «60с назад» отравлена высокими значениями до падения (граница корзин 80→81 и т.п.), путь тренда не открывается при росте, и рывок +25% принимает скачок больше порога — возврат «пилы».
- **Полная зарядка (raw = 0) принимается мгновенно**: EMA не должна «дотухать» десятки секунд до нуля после isFull (терминальный факт).

### D7. Гейт опоры — подключение, а не статус CHARGING
`ChargeForecaster.forecast()` перестаёт требовать `isCharging`: раз сессия уже идёт (её старт — переход `isPlugged`), цифры определяются только наличием опоры (скорость не-null и не мусорная). Рампа с ещё не подтверждённым CHARGING при наличии истории → цифры с первой секунды (сценарий спеки). Изменение параметра `isCharging: Boolean` на семантику «сессия активна» — уточнить при реализации, чтобы не оставить мёртвый параметр.

### D8. Подпись точности — без изменений
Вся фаза смеси (≤180с) попадает в существующее «Примерно» (до 90с и до 10 минут — оно и так «Примерно»). Новая строка «по истории» отвергнута: дополнительная локализация без роста честности — смесь и так маркируется как приблизительная.

## Risks / Trade-offs

- [Приор не про эту пару зарядка+кабель (буфер на chargeType смешивает AC-зарядки)] → ущерб ограничен фазой 180с (w→0), фильтр показа гасит рывки; полноценное решение — профили, Non-Goal этого change.
- [Тихая ошибка при маленьком расхождении: пересмотр истории вверх на величину ниже порога шума тренд-путь не откроется, ошибка в 1-2 минуты живёт до конца сессии] → принимается: в пределах цели ±10 минут; порог — константа, можно опустить при контроле property-теста.
- [Калибровка TREND_NOISE_FLOOR_SEC: слишком низок — property-тест падает на белом шуме, слишком высок — антипила-тест не проходит] → оба теста с фиксированными сидами написать раньше константы (пишущий тест видит падение и подгоняет); итоговое значение — результат обоих, не «на глаз».
- [Регрессия fusion при удалении приора из яруса 0] → `SpeedFusionTest` обновляется в том же изменении: ни один тест не удаляется без эквивалентной замены под новый контракт (правило проекта); сценарии «мусорный ток + движущийся уровень» остаются и продолжают закрываться.
- [Двойной источник приора: остаётся `KEY_LAST_SPEED` рядом с буфером] → `KEY_LAST_SPEED` перестаёт читаться движком (нужен только на время миграции D5 и может быть удалён после); в задачи включена проверка, что `loadLastSpeed` никем не вызывается.
- [Смесь + DisplayFilter: два сглаживания подряд могут «замылить» быструю смену реальности] → нижнее сглаживание — EMA α=0.05 (≈20с) и только на live-вкладе; при w→0 цепочка идентична сегодняшней — регрессия невозможна по построению.

## Migration Plan

Пофазно, каждая фаза независимо тестируется и откатывается revert’ом:
1. **История** — буфер в `SessionCache` + запись из сводки + ленивая миграция + JVM-тесты. Ничего не читает — нулевой риск для конвейера.
2. **Смесь** — `HistoryBlender`, врезка в `SessionEngine`, удаление приора из `SpeedFusion`, гейт D7. Тесты: `HistoryBlenderTest`, обновлённые `SpeedFusionTest`/`SessionEngineTest`/`ChargeForecastTest`.
3. **Trend-gate** — `DisplayFilter` + тесты (property сохраняется, добавляется антипила).
4. **Сверка** — `.\gradlew.bat test`, `python scripts/check-version.py`, запись пользовательского блока changelog в `## [Unreleased]` (поведение видимое — плавный прогноз с первой секунды; пункт пишется в момент работы).

Фаза 2 без фазы 3 работает как «пила» текущего фильтра (как сегодня) — допустимо кратковременно, фаза 3 обязательна до релиза.

## Open Questions

- Порог ускоренного ухода от истории при сильном расхождении с живыми замерами (например, w×0.5 при divergence > 40% до истечения 180с): ускорил бы смену «не той» зарядки, но меняет апдейт-правила спекы — отложить до замера реальной ошибки на устройстве автора (фаза 3 калибровки).
- Размер буфера N=5 и медиана — подтвердить на реальной истории после накопления сессий; замена агрегата (напр. взвешенная по свежести медиана) не меняет спеку, только константу.
