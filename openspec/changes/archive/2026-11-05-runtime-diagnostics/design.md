# Design

## Context

Сейчас состояние конвейера не покидает `SessionEngine`: наружу уходит только `SessionState` с готовыми числами, а промежуточные величины (ёмкость, отдельные спидометры, множитель корзины, сырой остаток до фильтра) никуда не попадают. Единственный журнал — `DischargeJournal` — пишет только разряд и лежит в `files/discharge-journal.txt`, недоступном на релизной сборке. См. proposal.md — Why.

Ограничения, которые формируют решение:
- тик идёт раз в секунду на зарядке; запись в файл из потока расчёта недопустима;
- журнал должен читаться человеком и грепаться без инструментов;
- приложение работает на телефоне с агрессивной оболочкой: лишние пробуждения и дисковая запись нежелательны;
- релизная сборка не debuggable, значит выгрузка обязана идти через UI.

## Goals / Non-Goals

**Goals:**
- След тика и события, пригодные для разбора инцидента вида «0 с при 81%» без участия разработчика рядом с телефоном.
- Выгрузка журнала из релизной сборки.
- Отказ записи не влияет на прогноз.
- Убрать повторные обращения к запрещённым узлам данных и связанный шум в системном логе.

**Non-Goals:**
- Изменение расчётных формул, порогов и показываемых чисел.
- Удалённая телеметрия, сеть, аналитика, crash-репортинг.
- Полноценный «журнал истории сессий» для пользователя (это отдельная будущая фича).
- Замена существующего `DischargeJournal` — он остаётся как есть до отдельного решения.

## Decisions

### D1. Снимок тика формирует движок, пишет — приложение
`SessionEngine` при каждом `update()` собирает неизменяемый `DiagTick` (структура из примитивов) и кладёт его в `@Volatile`-поле; `ChargeForecastApplication` читает его в своём коллекторе состояния и передаёт в `DiagLog`.

Почему не вызов `DiagLog.record()` прямо из движка: движок остаётся чистым для JVM-тестов (в нём нет ни Android, ни файлов), а запись перестаёт быть частью расчёта. Почему не расширять `SessionState`: состояние читают экран и виджет, и лишние поля в нём увеличивают стоимость каждой пересборки.

Альтернатива — писать всё из `BatteryMonitor`: отклонена, у монитора нет ни ёмкости, ни смеси с историей, то есть половины нужных величин.

### D2. Один формат строки: `key=value` через `;`
Пример: `t=1234567;lvl=81;st=2;plug=AC;ma=4;cnt=3268000;cap=4035200;s1=2.94;s2=-;s3=3.01;f=3.01;base=5.47;k=0.55;raw=676;shown=671;acc=PRECISE`.

Почему: читается глазами, режется `Select-String`/`grep`, не требует парсера, устойчив к добавлению полей в конец. CSV отклонён — в нём легко сдвинуть колонки; JSON избыточен по объёму для 1 Гц.

Отсутствующая величина пишется как `-`, а не пропуском поля: тогда число полей постоянно и разбор не ломается.

### D3. Единственный писатель и ограниченная очередь
`DiagLog` держит `Channel(capacity = 256, DROP_OLDEST)` и одну корутину на `Dispatchers.IO`, которая пишет строки. Публикация — `trySend`, без ожидания.

Почему: гарантирует порядок строк, не блокирует тик, при переполнении теряет старые строки, а не свежие, и переживает медленный диск.

### D4. Троттлинг: тик — 1 Гц, события — всегда
Строка тика пишется не чаще раза в секунду (на зарядке это ровно тик, в остальное время — не пишется вовсе). События (ёмкость, точность, статус слежения, отказ сервиса, качество датчиков) пишутся сразу и не троттлятся, кроме дедупликации одинаковых подряд.

Почему: 1 Гц × 2 файла по 1 МБ — это примерно 8–10 часов зарядки; для разбора инцидента достаточно, а роста вне зарядки нет вовсе.

### D5. Файлы: `files/diag/session.log` + `session.log.old`
Ротация одноуровневая по достижении 1 МБ, как у существующего `DischargeJournal`. Каталог `files/diag/` исключается из backup и data-extraction, как `discharge-journal.txt`.

Почему не одна большая свалка: ротация по размеру уже отработана в проекте, а два файла дают историю «до и после» инцидента.

### D6. Выгрузка через `FileProvider` + `ACTION_SEND`
Кнопка в настройках рядом с версией. Файл отдаётся провайдеру по `content://`, тип `text/plain`, заголовок — «Диагностика ChargeForecast».

Почему не «сохранить в Downloads»: share работает на любой оболочке, включая EMUI, и не требует разрешений на внешнее хранилище. Почему не `adb`: на релизной сборке путь недоступен.

### D7. Negative-cache для чтения узлов данных
`SysfsCurrent`/`SysfsCapacity` получают общий `SysfsProbe`: первый отказ (нет файла, `EACCES`) запоминается в `@Volatile`-множестве путей, и повторное чтение того же пути в этом процессе не выполняется.

Почему: на устройстве автора чтение `/sys/class/power_supply/battery/*` запрещено SELinux, и приложение получает 1–2 `avc: denied` в секунду, забивая системный лог и выполняя бесполезную работу. Альтернатива «пробовать раз в минуту» оставлена на потом: сначала проверим, что одного раза за процесс достаточно.

### D8. Никаких изменений в расчёте
Ни один порог, множитель и ярус точности этим change'ем не меняется — иначе станет невозможно отличить эффект наблюдаемости от эффекта правки модели. Ярусы, формулы и показ остаются как есть; их меняет следующий change (`forecast-integrity`).

## Risks / Trade-offs

- **[Запись на диск раз в секунду на зарядке]** → 1 Гц только на зарядке, асинхронная очередь, ротация 2 × 1 МБ; замер батареи до/после на устройстве в рамках tasks.
- **[Строка тика «утяжеляет» горячий путь]** → сборка строки вынесена в писателя (в очередь кладётся структура, а не текст); в движке только присваивание поля.
- **[FileProvider легко настроить неверно (пути, authority)]** → отдельная задача на ручную проверку выгрузки на устройстве, включая пустой журнал.
- **[Журнал содержит данные, которые пользователь не хочет отдавать]** → в журнале только числа батареи и идентификаторы состояния, без путей, аккаунтов и текста сообщений; выгрузка — только по явному действию.
- **[Negative-cache «залипнет» на источнике, который на самом деле доступен]** → кэшируется только отказ по конкретному пути; перезапуск процесса сбрасывает; успешное чтение ничего не кэширует.
- **[Дублирование с DischargeJournal]** → признаём: два журнала живут параллельно до отдельного решения об объединении; в этом change'е старый не трогаем.

## Migration Plan

Миграции данных нет: новые файлы создаются при первом тике, старый `discharge-journal.txt` продолжает работать. Откат — удалить каталог `files/diag/` и снять вызов из коллектора; формулы и хранилища не затронуты, поэтому откат безопасен в любой момент.
