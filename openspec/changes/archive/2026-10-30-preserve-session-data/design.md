# Design: preserve-session-data

## Context

См. `proposal.md` — Why. Текущее состояние, важное для подхода:

- `DischargeSample.atMs` и `SessionEngine.plugDetectedAtMs` — это `elapsedRealtime`; после ребута шкала начинается заново, поэтому метки разных загрузок несравнимы (`DischargeEstimator.kt:8-15`, `SessionEngine.kt:42-43`).
- `DischargeEstimator.restore()` слепо загружает сэмплы, а `prune()` удаляет только те, что старше `now - 24h` (`DischargeEstimator.kt:123-132, 294-302`). После ребута `cutoff` отрицательный, старые сэмплы остаются.
- `SessionEngine` хранит активную сессию только в памяти; в кэш пишутся ёмкость, сводка и история, причём сводка — только при отключении кабеля (`SessionEngine.kt:42-89`).
- `SessionCache` — один `SharedPreferences`-файл `charge_session_cache` для ёмкости, сводки, истории, кривой и состояния разряда; backup-правила пустые (`SessionCache.kt:13-17, 85-105`, `backup_rules.xml`).
- `SessionState` не содержит служебного снимка сессии; UI и виджету он не нужен.

## Goals / Non-Goals

**Goals:**

- Одинаково понимать «процесс умер» и «устройство перезагрузилось»: в первом случае продолжать сессию, во втором — корректно её закрыть.
- Не допускать смешивания `elapsedRealtime` разных загрузок в окне разряда.
- Сохранить сводку активной сессии при смерти процесса и не записать её дважды.
- Оставить `DischargeEstimator` и `SessionEngine` тестируемыми на JVM, без Android-зависимостей в расчётных классах.

**Non-Goals:**

- Health-check сервиса, `TrackingHealth`, баннеры ошибок и `MY_PACKAGE_REPLACED` — следующий change.
- История сессий в UI, профили, сравнение зарядок/кабелей.
- Изменение математики прогноза, окна 24 ч, приоров и кривой доводки.
- Сохранение всех транзиентных полей движка (EMA, фильтр показа) — после восстановления они пересоберутся.

## Decisions

### D1. Boot identity — отдельный снимок загрузки

Ввести `BootIdentity`:

```kotlin
data class BootIdentity(
    val bootCount: Int?,      // Settings.Global.BOOT_COUNT, null если недоступен
    val wallClockMs: Long,
    val elapsedRealtimeMs: Long
)
```

`BootIdentity.current(context)` читает `BOOT_COUNT`; `null` — осознанная деградация на OEM, где настройка недоступна.

Персистить `bootCount` вместе с `DischargeState` и `ActiveSessionSnapshot`. При восстановлении:

- если оба `bootCount` известны и различаются — загрузка сменилась;
- если `bootCount` неизвестен — считать загрузку сменившейся, когда сохранённый `elapsedRealtime` больше текущего (после ребута шкала сбросилась); это консервативная эвристика, а не гарантия;
- wall-clock использовать только для диагностики/якоря, не для расчёта окна.

**Альтернатива:** пересчитывать старые `atMs` по wall clock. Отвергнута: появляется зависимость от перевода часов и нужна сложная валидация; для 24-часового среднего честнее начать окно заново.

### D2. Политика восстановления: same boot — resume, new boot — finalize

| Событие | Окно разряда | Активная сессия |
|---|---|---|
| Смерть процесса, та же загрузка | восстановить сэмплы | продолжить с прежним стартом |
| Ребут | сбросить сэмплы, приор | закрыть по последнему уровню, сводка один раз; если кабель подключён — новая сессия |
| Backup / другое устройство | сбросить сэмплы | активной сессии нет; новый старт |

После ребута `elapsedRealtime` непригоден для возраста сессии, поэтому склейка через ребут запрещена. Сводка старой сессии считается по сохранённым `startedAtMs`, `lastUpdatedAtMs` и уровням — это корректно внутри старой загрузки.

### D3. Снимок активной сессии — только необходимое

`ActiveSessionSnapshot`:

```kotlin
data class ActiveSessionSnapshot(
    val id: String,                 // UUID сессии, для идемпотентной финализации
    val bootCount: Int?,
    val startedAtMs: Long,          // elapsedRealtime
    val startLevelPct: Int,
    val chargeType: ChargeType,
    val ccSpeedSum: Float,
    val ccSampleCount: Int,
    val peakCurrentUa: Long?,
    val lastLevelPct: Int,
    val lastUpdatedAtMs: Long
)
```

`SessionEngine` отдаёт снимок и умеет восстанавливаться из него:

- восстанавливаются старт, уровень, тип, пик, накопитель CC;
- `historyBaseRate` и `taperFactors` перечитываются из `SessionCache` по типу подключения;
- транзиентные спидометры, EMA, `DisplayFilter` и `CapacityTracker` сбрасываются и пересобираются с первых секунд после восстановления.

**Почему не полный снимок движка:** он включает полдюжины внутренних полей с тонкими инвариантами; ошибка в одном поле даст неверный прогноз, который трудно заметить. Сброс транзиентов даёт короткий «разгон» после kill, но сохраняет честную базу сессии и сводку.

`CcPhaseAccumulator` получает `snapshot(): Pair<Float, Int>` и `restore(speedSum, sampleCount)` — иначе средняя CC-скорость после kill потеряется.

### D4. Отдельное runtime-хранилище

Волатильные и boot-bound данные переезжают в `SessionRuntimeStore` (`session_runtime` prefs):

- `bootCount`;
- `discharge_samples_v2` и якоря;
- `active_session_*`;
- `capacity_uah` (ёмкость привязана к конкретной батарее).

`SessionCache` остаётся хранилищем сводки, истории и кривой. `backup_rules.xml` и `data_extraction_rules.xml` исключают `session_runtime.xml` и `discharge-journal.txt`; переносить чужие метки и ёмкость на новое устройство нельзя.

**Альтернатива:** оставить один файл и исключить его целиком. Отвергнута: тогда на новом устройстве теряются история и кривая, хотя они не boot-bound. Разделение даёт точную границу «переносимое / машинное».

### D5. Запись снимка — с троттлингом

Снимок активной сессии пишется не чаще раза в 10–30 с и дополнительно на границах уровней/старте/финише. Это ограничивает потерю прогресса при kill тридцатью секундами и не возвращает запись в SharedPreferences раз в секунду.

### D6. Финализация сводки — идемпотентная

`ActiveSessionSnapshot.id` попадает в `SessionSummary.id` (nullable, для старых записей). Финализация:

1. если `cache.loadSummary()?.id == snapshot.id` — сводка уже записана, только очистить runtime-снимок;
2. иначе сохранить сводку, затем очистить снимок.

Порог качества остаётся прежним: средняя CC-скорость ≥ 0.1 %/мин и набрано ≥ 2%. Если порог не пройден, снимок очищается без сводки.

### D7. Порядок восстановления при старте Application

`ChargeForecastApplication.onCreate()`:

1. создать `SessionCache` и `SessionRuntimeStore`;
2. прочитать `BootIdentity`;
3. восстановить/отбросить `DischargeState`;
4. прочитать `ActiveSessionSnapshot`;
5. если загрузка та же — передать снимок в `ChargeSessionMonitor`/`SessionEngine`;
6. если загрузка сменилась — финализировать старую сессию и очистить снимок, затем стартовать монитор без активной сессии.

Монитор создаётся после восстановления, поэтому первый `state` уже отражает правильную сессию, а не пустой старт.

## Risks / Trade-offs

- [Потеря до 30 с прогресса при kill] → троттлинг 10–30 с; на финише и границах уровней снимок пишется сразу.
- [После ребута оценка разряда падает на приор] → это честнее смеси двух шкал; в UI уже есть пометка «≈».
- [BOOT_COUNT недоступен на части OEM] → консервативная эвристика по `elapsedRealtime`; при сомнении выбираем сброс, а не склейку.
- [Сводка после ребута может быть неполной: последние 30 с не учтены] → порог 2% и средняя CC-скорость остаются; сессия всё равно полезнее, чем потерянная.
- [Разделение prefs — миграция] → старые ключи `discharge_*`/`capacity_uah` в `charge_session_cache` игнорируются; новые ключи пишутся в runtime. Откат на старую версию не ломает установку, но старый баг после ребута вернётся.
- [Идемпотентность на двух файлах неатомарна] → id сессии и проверка `loadSummary().id`; худший случай — повторная финализация не создаёт вторую сводку.

## Migration Plan

1. Добавить runtime-хранилище и boot identity; старые ключи не читать.
2. При первом запуске новой версии `DischargeState` без `bootCount` считать несовместимым и начать окно заново (старые сэмплы не использовать).
3. Старую сводку/историю/кривую оставить в `charge_session_cache`; `SessionSummary.id` для старых записей = `null`.
4. Проверить на устройстве: `adb reboot`, `am force-stop`, отключение кабеля при мёртвом процессе, восстановление из backup.
5. Откат: предыдущий APK; новые ключи игнорируются, старые данные не удаляются.
