# Design

## Context

Сейчас остаток складывается из двух несовместимых половин: доля остатка берётся из счётчика (`ёмкость − счётчик`), а кривая доводки — из уровня (`TaperCurve.remainingMinutes` идёт по целым процентам уровня). Скорость на экране — мгновенная оценка fusion, а остаток — интеграл по модели, поэтому числа не связаны уравнением. Ёмкость оценивается из одного замера (`counter·100/level`) и уточняется коридором ±20%, который не имеет памяти о направлении: после неудачного шага вниз вернуться уже нельзя, потому что коридор считается от испорченного значения.

На устройстве автора паспортная ёмкость недоступна: `/sys/class/power_supply/battery/*` закрыт SELinux, `SysfsCapacity` возвращает `null`. Значит защита не может опираться только на design capacity.

См. proposal.md — Why и дельту `charge-forecast` для требований.

## Goals / Non-Goals

**Goals:**
- Один источник истины для заряда и один для ёмкости; инварианты проверяются в одном месте и в тестах.
- Остаток в энергии насквозь, уравнение «остаток = энергия ÷ скорость» выполняется на экране.
- Ноль и «точно» становятся недостижимы на противоречивых данных.
- Состояние «на кабеле, но не заряжается» перестаёт маскироваться под зарядку.

**Non-Goals:**
- Переделка fusion трёх спидометров и DisplayFilter (отдельный change после трасс; здесь меняется только гейт нуля и привязка к `isFull`).
- История сессий, профили «зарядка + кабель», экраны истории.
- Оценка разряда и её 24-часовое окно.
- Слежение, виджет, сервис — их касается только текст состояния.

## Decisions

### D1. Источник истины: счётчик, уровень — граница и резерв
Заряд в батарее берётся из `CHARGE_COUNTER`; уровень используется для корзин доводки, для показа и как резерв, когда счётчика нет. Смешивать их в одной формуле (как сейчас: остаток из счётчика, корзины из уровня) больше нельзя — это и есть источник несогласованности.

Альтернатива «считать всё по уровню» отклонена: квантование 1% даёт шаг в минуты и убивает смысл счётчика. Альтернатива «считать всё по счётчику, включая корзины» — принята, см. D3.

### D2. Ёмкость: три эшелона защиты
```
cap0 = counter·100/level                        // старт сессии
эшелон 1: cap ∈ [0.85·design, 1.15·design]      // если design известна
эшелон 2: cap ≥ counter·1.02, cap ∈ [0.5 А·ч, 30 А·ч]
эшелон 3: шаг уточнения ≤ 12% от текущей оценки
```
Уточнение принимается только при `Δlevel ≥ 2` и `Δcounter > 0` и только если новый шаг не выходит за 12%. Три отклонённых подряд уточнения — сигнал, что оценка уехала: сброс к `counter·100/level`.

Почему 12%, а не 20%: инверсия `cap ≤ counter` на уровне 81% требует шага ≥19% вниз; при 12% она недостижима одним шагом, а три подряд отклоняются порогом «три подряд». Почему не «жёсткий ±5%»: живой дрейф на деградировавшей батарее иначе не отследить.

### D3. Остаток в энергии, корзины по энергии
```
remainingUah = max(cap − counter, 0.005·cap)     // 0.5% — минимальный остаток, не ноль
шаг = cap/100                                    // 1% энергии
пока remainingUah > 0:
    доля = min(remainingUah, шаг)
    время += доля / (baseRate·factor(level + i))
```
Множитель берётся по уровню, на котором находится очередной шаг энергии, но шаг — энергетический. Это сохраняет форму кривой (плавный переход через 80%) и убирает смешение единиц.

Альтернатива «оставить проценты уровня и пересчитывать энергию в проценты» отклонена: тогда снова появляется два пространства.

### D4. Показываемая скорость — эффективная
`effectiveSpeed = remainingPct / (ETA/60)`. Это та скорость, по которой реально посчитан остаток, включая замедление. Мгновенная скорость остаётся входом для base rate, но на экран не попадает.

Альтернатива «показывать обе» отклонена: два числа снова противоречат друг другу, а экран у нас минималистичный. Если позже понадобится «текущая скорость», это отдельная строка с явной подписью.

### D5. Гейт точности
`PRECISE` присваивается только при: возрасте сессии ≥ 10 мин, согласии спидометров, `инварианты выполнены` и `остаток не резервный`. Иначе — не выше `APPROXIMATE`. `REFINING` сохраняет приоритет.

Почему не отдельный ярус «данные недостоверны»: интерфейс уже имеет три подписи, четвёртая потребует объяснения; понижение до «Примерно» честно и не расширяет UI.

### D6. Состояние «кабель подключён, зарядка не идёт»
В движке появляется `ChargePhase`: `CHARGING`, `FULL`, `STALLED`. `STALLED` ставится, когда кабель подключён, статус не CHARGING/FULL и уровень не рос 60 замеров подряд; снимается при возврате CHARGING или росте уровня. В `STALLED` прогноз до 100% не выдаётся, экран показывает текст и оценку работы (существующая карточка разряда).

Почему 60 замеров, а не «сразу»: Huawei держит паузу умной зарядки на 80%, и мгновенная реакция давала бы мигание туда-обратно на каждой паузе.

### D7. Достоверность тока
`currentMa` заполняется только при `currentUa ≥ 50 000` в состоянии зарядки. Ниже — `null`, и `BatterySensorTracker` через три замера покажет MISSING, включив существующее пояснение о резервном источнике.

Почему 50 мА: на 4 А·ч это 0.075 %/мин — ниже порога доверия спидометра (0.05 %/мин) по порядку величины; всё, что меньше, не влияет на прогноз, но засоряет экран.

### D8. Золотые трассы вместо веры в формулы
Три записанные последовательности снапшотов (шаг 1 с): AC-зарядка 60→100%, слабый USB с паузами, «кабель есть, зарядки нет». Тест гоняет `SessionEngine` тик за тиком и проверяет инварианты I1–I5 и монотонность остатка.

Почему не только юнит-тесты формул: текущие 245 тестов зелёные при баге «0 с». Инвариант проверяется на поведении движка, а не на отдельной формуле.

## Risks / Trade-offs

- **[Привычные числа изменятся]** — эффективная скорость ниже мгновенной на доводке, остаток станет согласованным. → Отражено в changelog пользовательским блоком; живая проверка на устройстве.
- **[Паспортная ёмкость недоступна на P20]** — эшелон 1 вырождается. → Эшелоны 2 и 3 остаются; инвариант `cap > counter` работает всегда.
- **[Энергетические корзины меняют форму остатка у 80%]** — возможен скачок на границе. → Тест плавности на трассе 60→100%, допуск как в текущем `forecast_taperInterpolation_smoothAcrossEighty`.
- **[STALLED ложно срабатывает на паузе умной зарядки]** — это целевое поведение, но текст должен быть нейтральным («кабель подключён, зарядка не идёт»), а не «ошибка».
- **[Сброс ёмкости по трём отклонённым шагам может «дёргать» оценку]** — сброс только при трёх подряд и с событием в диагностику; трассы покажут частоту.
- **[Golden traces синтетические]** — риск подгонки под них; закрывается живой проверкой с диагностикой из `runtime-diagnostics`.

## Migration Plan

Данные не мигрируют. Сохранённая ёмкость (`session_runtime.capacity_uah`) при чтении проходит эшелон 2: значение, не проходящее инвариант, игнорируется и пересчитывается из текущего замера. Откат — вернуть прежние `ChargeForecaster`/`CapacityTracker`; хранилища не меняются, поэтому откат безопасен в любой момент.
