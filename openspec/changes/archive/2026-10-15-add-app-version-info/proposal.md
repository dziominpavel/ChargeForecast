# Proposal: add-app-version-info

## Why

Пользователю негде увидеть, какая версия приложения установлена, — при баг-репортах и проверке «встал ли апдейт» приходится лезть в системные настройки. Версионная инфраструктура уже готова: `BuildConfig` генерирует `VERSION_NAME` (из файла `version`), `VERSION_CODE` и `BUILD_DATE`, но UI их не читает ни разу.

## What Changes

- Внизу экрана настроек появляется статичная строка вида «ChargeForecast 0.4.2 · сборка 14.10.2026» — версия приложения и дата сборки.
- Тап по строке не обрабатывается: отказываемся от идеи «тап копирует версию» (проще, scope минимальный).
- `VERSION_CODE` в лоб не показываем: значение вида `2_000_100_131` нечитаемо для пользователя.
- Строки и отступы — только через ресурсы `strings.xml` и токены темы (`ChargeDimens`, `MaterialTheme.typography`), без inline-констант.

## Capabilities

### New Capabilities

_(нет)_

### Modified Capabilities

- `app-settings`: новое требование — экран настроек в нижней части показывает версию приложения и дату сборки; значения берутся из `BuildConfig` на момент сборки и не меняются во время работы.

## Impact

- `app/src/main/java/com/example/chargeforecast/ui/SettingsScreen.kt` — нижний блок (Spacer с весом + тексты); первое чтение `BuildConfig` в UI.
- `app/src/main/res/values/strings.xml` — новая строка-шаблон версии (секция «Настройки»).
- `CHANGELOG.md` — пользовательский буллет `**Добавлено**` + инженерная деталь под `### Добавлено` (правила versioning).
- Связь с активным change `fix-widget-and-discharge-remaining`: он меняет другое требование `app-settings` (поведение кнопки «назад») — дельты не пересекаются, порядок архивации произвольный.
- Сборка, разрешения, сервисы, виджет — не затрагиваются.
