## Context

См. proposal.md — Why. Текущее состояние `SpeedFusion.fuse()`: ярусы 0-20 / 20-90 / 90+ сек, мусор-фильтр `credible()` с льготой для доводки (`levelPct >= TAPER_START_LEVEL`), приоритет `s1 ?: s2 ?: s3` в ветке `else`. Вызов из движка уже передаёт `levelPct`, константы порогов (`MIN_CREDIBLE_SPEED_PCT_PER_MIN = 0.05`, `DIVERGENCE_LIMIT = 0.40`) на месте. Прогнозировщик и движок не меняются — чинится только выбор итоговой скорости.

## Goals / Non-Goals

**Goals:**
- Мусорный ток/счётчик никогда не побеждают движущийся уровень ни в одном ярусе.
- Поведение в остальных случаях — бит-в-бит как сейчас (все существующие тесты fusion остаются зелёными без правок).

**Non-Goals:**
- Зеркальный кламп вверх (итог в разы выше S3) — отдельный follow-up change.
- Детекция паузы зарядки при замершем уровне, sysfs-источники тока.

## Decisions

### D1. Вето — пост-фильтром поверх результата яруса, а не новой веткой
После вычисления кандидата действующими правилами ярусов применяется одна проверка: `s3 >= 0.2 && (candidate == null || candidate < 0.3 * s3)` → итог `Fused(s3, refining = false)`. Почему пост-фильтр, а не правка каждой ветки: правило одно на все ярусы (включая tier1, где сейчас вообще нет fallback на S3), дифф — десяток строк в одном месте, все старые ветки и их тесты не трогаем.

### D2. Порог здоровья S3 — 0.2 %/мин, а не порог доверия 0.05
0.05 — это порог «не мусор рампы», но уровень, ползущий 0.1 %/мин по одному шагу за 10 минут, — слабый свидетель. 0.2 %/мин (≈1% за 5 минут) — это уже явное движение, которому можно доверять против мусорных 0.003. Альтернатива (доверять любому non-null S3) отвергнута: кооперативный сценарий «пауза зарядки с дрожащим уровнем» давал бы ложные вето.

### D3. Коэффициент вето 0.3, refining=false при срабатывании
Кандидат ниже 30% от здорового S3 — это не «расхождение», а мусор: статус обычный (по ярусам точности), не «уточняю». 0.3, а не 0.5/0.8 — запас против отставания S3 (окно 10 мин, квант 1%): при честном расхождении S1/S2 в пределах ±40% вето не должно срабатывать ложно. Альтернатива (класть вето внутрь `refining=true`) отвергнута: refining означает «не уверены», а здесь мы уверены — уровень едет.

### D4. Tier1 тоже под вето (как fallback, не как источник)
В tier1 кандидат — S2/приор; если он null, а S3 здоров — итог S3. Это буквально требование «цифры с первой валидной опоры» из спеки: S3 на 15-й секунде суперзарядки — валидная опора. Приор при этом не трогаем: здоровый приор (≥0.3×S3) побеждает лагнувший S3 как раньше.

## Risks / Trade-offs

- [Устаревший S3 при паузе зарядки] → вето требует s3 ≥ 0.2, а замерший уровень быстро даёт S3 — null; остаточный риск (пауза сразу после шага) ограничен окном ~10 мин и покрыт регрессией «пауза → нет вето».
- [Пороги 0.2/0.3 откалиброваны по одной живой сессии] → в регрессии зафиксированы числа автора (87→90, 7 мА); следующая живая сессия либо подтвердит, либо уточнит — отдельной задачей калибровки, не в этом change.
- [Вето маскирует реально сломанный S1/S2 вместо их чинки] → принято осознанно: уровень — единственный ground truth из коробки устройства; чинка sysfs-источников — отдельная работа по дампу прошивки.

## Migration Plan

Шаги внутри change: unit-тест fusion с числами автора (сначала красный) → вето в `SpeedFusion.fuse` → engine replay-тест 87→90 → полный прогон `test`. Откат — удаление пост-фильтра (один блок), остальной fusion не тронут.
